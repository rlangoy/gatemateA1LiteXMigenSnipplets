## Description

Intermittent character corruption occurs in the BIOS console when `--uart-fifo-depth` is set to 16, 64, or 256. The issue does **not** reproduce with `--uart-fifo-depth 4`.

Typing `help` echoes `h%lp` (or similar corruption). Pressing Enter still executes the correct command, indicating the RX path is unaffected.

## Environment

- **Board:** Olimex GateMate A1-EVB Rev.C (2025)  
- **CPU:** PicoRV32 @ 24 MHz (`--cpu-variant minimal`)  
- **LiteX SHA:** `9a52a3a4a`  
- **Build command:**
```
  python3 -m litex_boards.targets.olimex_gatemate_a1_evb \
      --cpu-type picorv32 --cpu-variant minimal \
      --uart-fifo-depth 64 --build --load
```

## Steps to Reproduce

1. Build and flash with `--uart-fifo-depth 64` (or 16/256).
2. Connect: `litex_term /dev/ttyACM0`
3. Type `help` → observe corrupted echo (e.g. `h%lp`).
4. Press Enter → command executes correctly.

## Expected Behaviour

Characters echo cleanly with no corruption regardless of FIFO depth.

## Workaround

Using `--uart-fifo-depth 4` eliminates the corruption.

## Root Cause (suspected)

A multiple-driver conflict on `self.source.valid` in `add_auto_tx_flush()`. The method inserts a `flush_ep` endpoint and drives `self.source` via a second `comb` assignment, creating two combinational drivers on the same net when the FIFO depth is large enough to expose the race.

## Proposed Fix

Replace the intermediate `flush_ep` stream with a single gated-valid signal (`_tx_flush_valid`) allocated in `__init__`, ensuring exactly one combinational driver per net at any FIFO depth.

The fix gates `source.valid` (not `source.ready`) so the PHY always completes the current byte before the flush logic can influence what is loaded next, eliminating the corruption.
